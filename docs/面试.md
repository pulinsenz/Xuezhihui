# 全套面试口述问答稿（AI‑Agent 开发实习，你的多 Agent 协同 RAG 项目）

> 定位：SpringBoot Java 业务后端 + Python FastAPI+LangGraph 双服务多 Agent‑RAG 系统 全部口语化，面试直接复述，覆盖：项目背景、架构选型、边界划分、RAG 优化、Agent 设计、坑点、降级、部署。

## 1、项目简单自我介绍（开场 1 分钟）

> 面试官：简单介绍下你这个项目。

**口述：** 我做的是一套多 Agent 协同 RAG 知识库问答系统。项目采用双服务架构，Java SpringBoot 负责业务层，处理用户鉴权、知识库元数据管理、对话记录存储；Python 基于 FastAPI+LangGraph 实现 AI Agent 核心逻辑。 我把 Agent 拆成五个角色，通过状态图实现任务分发、检索、工具调用、反思校验、回答生成，还支持证据不足自动重新检索的闭环。RAG 这边做了向量 + BM25 混合检索，搭配交叉编码器重排，同时用反思 Agent 抑制大模型幻觉。 服务之间通过 HTTP 和 SSE 流式通信，Redis 用来共享会话和 Agent 状态；针对 Agent 推理耗时过长的问题，我做了异步任务方案规避超时；整套服务用 Docker Compose 一键编排，同时实现异常降级和链路埋点日志。

## 2、为什么选择 Java+Python 双服务，不全部用 Java 写 Agent？（高频必问）

**口述：** Java 生态里 SpringAI、LangChain4j 可以实现简单工具调用的 Agent，但缺少成熟的状态图引擎。我项目需要做多 Agent 流转、分支判断、证据不足触发二次检索这种循环闭环，如果用 Java 实现，状态维护、断点持久化都需要自己手写大量代码，开发成本高，稳定性也不好保障。 LangGraph 在 Python 这边生态非常成熟，原生支持状态管理、节点流转、循环重试，所以我把 Agent 相关逻辑独立成 Python 服务。业务部分交给 Java，Java 在权限、事务、数据库、并发这块企业级能力更强。

## 3、那为什么不全用 Python 开发，一套技术栈不更简单？

**口述：** 这个项目不只是简单问答原型，还包含用户登录、权限控制、知识库管理、对话记录管理这些完整业务模块。 Python FastAPI 做原型很快，但企业级业务组件、事务处理、权限管控不如 Java 成熟。 拆成两个服务还有一个好处：AI Agent 的计算压力可以独立扩容，大模型推理、RAG 检索的压力不会把业务服务拖垮，业务和 AI 可以单独部署扩缩容。

## 4、两个服务之间怎么交互？会话怎么打通？

**口述：** 有两种通信方式。实时对话场景，Java 调用 Python 的 SSE 流式接口，拿到 token 之后透传给前端，实现打字机效果。普通请求用 Feign 做 HTTP 调用。 因为 Agent 推理、工具调用经常耗时很久，同步 HTTP 容易超时，长耗时任务我做了基于 Redis List 的简易消息队列。Java 提交任务，Python 消费任务，前端轮询任务接口拿结果。

会话打通：sessionId 由 Java 生成，传给 Python。会话记忆、Agent 运行状态统一存到共享 Redis，两边都读写同一个 Redis 实例。MySQL 业务库只有 Java 能访问，Python Agent 不会直连 MySQL。

## 5、Python Agent 需要业务数据的时候怎么处理？怎么保证权限安全？

**口述：** Agent 禁止直接访问业务 MySQL。如果 Agent 需要业务数据，会作为工具回调 Java 开放的业务查询接口，请求带上鉴权 token。 鉴权、数据权限全部由 Java 这边校验，校验通过之后再返回业务数据。这样业务权限收敛在 Java 层，不会出现 Agent 越权读取数据的风险。

## 6、讲一下你的多 Agent 设计，五个 Agent 分别干什么，流转逻辑？

**口述：** 我基于 LangGraph 构建状态图，定义统一 State 对象，所有节点共享这份状态。一共五个 Agent 节点：

1. **路由 Agent**：接收用户问题，判断问题类型，是知识库问答、需要调用业务工具，还是闲聊，做任务分发。
2. **检索 Agent**：执行 RAG，做 BM25 + 向量混合检索，再经过交叉编码器重排，过滤掉无关文档片段。
3. **工具 Agent**：当需要业务数据时，回调 Java 接口获取业务数据，把结果写入状态。
4. **反思校验 Agent**：拿到检索或者工具返回的证据，做校验。判断现有证据能不能回答用户问题。如果证据不足、信息不够，就标记状态，跳转回检索 Agent，重新检索；证据充足就交给下一个节点。
5. **回答组装 Agent**：整合上下文和来源文档，生成最终答案，带上引用来源。

LangGraph 支持循环，反思判断证据不足，就回到检索节点，形成闭环；同时我加了最大循环次数限制，防止无限循环。

## 7、RAG 部分做了哪些优化？怎么解决幻觉问题？

**口述：** 检索层面，没有只用纯向量检索，采用 BM25 关键词检索加上向量检索做混合召回，弥补向量检索丢失关键词的缺陷；召回之后用交叉编码器重排，对文档做二次打分，过滤噪声文档，提升输入大模型的文档质量。 幻觉抑制分两层： 第一层靠检索质量，尽量给到模型准确的参考片段； 第二层是反思校验 Agent，专门校验答案和检索证据是否匹配。如果证据不足以回答问题，不会强行编造答案，会告知用户缺少相关信息，同时支持触发二次检索。 文档预处理这边做了语义分块，配置重叠窗口，减少上下文割裂。

## 8、项目遇到哪些坑？怎么解决？（工程化重点，面试官很爱听）

### 坑 1：Agent 推理、工具调用时间长，HTTP 同步调用超时

> 口述： 最开始直接同步 HTTP 调用，复杂多轮 Agent 很容易超时。解决方案：区分两种场景，实时对话走 SSE 流式；长耗时任务走 Redis 消息队列异步处理，前端轮询任务状态，规避接口超时。同时 Feign 也调大超时时间。

### 坑 2：上下文无限膨胀，token 越来越大

> 口述： 会话记忆做窗口裁剪，Redis 里保存对话历史，保留最近 N 轮，避免上下文无限变长，减少 token 消耗，防止大模型报错。

### 坑 3：LangGraph 无限死循环

> 口述： 反思 Agent 可以跳回检索节点，理论上会无限循环。我在 State 里面增加循环计数器，设置最大重试次数，到达阈值直接终止流程返回提示。

### 坑 4：两个服务联调，状态不同步

> 口述： 最开始把会话状态分别存在 Java 和 Python 各自内存，一旦服务重启状态丢失。后面统一迁移到共享 Redis，所有会话、Agent 状态外部存储，服务重启不丢失。

### 坑 5：Agent 服务挂掉，Java 直接报错抛给前端

> 口述： Java 调用 Python 的时候做异常捕获，增加降级策略，如果 Agent 服务不可用，返回友好业务提示，而不是把原始异常抛到前端。

## 9、向量库为什么选 Milvus，为什么不用 Chroma？

**口述：** Chroma 适合本地原型测试，数据量上来性能一般。Milvus 是生产级向量数据库，支持多种检索参数，支持分片，后续项目数据量变大可以水平扩展，更贴合项目工程化定位。

## 10、如何做可观测？

**口述：** 我对 Agent 每一步节点做埋点日志，记录路由结果、召回文档数量、重排保留数量、是否触发二次检索、token 消耗、每一步耗时。 排查幻觉、检索失败的时候，可以直接看日志定位是检索的问题，还是大模型生成的问题。没有引入较重 ELK，用结构化日志输出，便于后续对接日志组件。

## 11、如果让你继续优化这个项目，你会做什么？（拓展题）

**口述：**

1. 增加 RAG 自动评测链路，用数据集自动评估召回率、答案准确率；
2. 接入真正的消息队列 RabbitMQ/RocketMQ 替代 Redis List 简易队列，提升可靠性；
3. Agent 状态持久化落库，支持断点续对话；
4. 增加限流，防止大模型接口被打满；
5. 增加多租户隔离，不同知识库之间数据隔离。

## 12、追问：LangGraph 的 State 原理简单说下

**口述：** State 是整个图的共享状态对象，各个节点只读取和修改 State，节点之间不直接传参。每一个节点执行完输出更新 state，图根据 state 里面的条件做分支跳转。状态可以持久化到 Redis，中断之后可以恢复执行。

## 13、追问：SSE 流式的流程，Java 这边做了什么？

**口述：** 前端建立 SSE 连接请求 Java；Java 内部调用 Python Agent 的 SSE 流式接口；Java 拿到 Python 返回的每一块 token，再通过 SseEmitter 转发给前端。Java 起到转发和鉴权的作用，真正 token 生成在 Python Agent 服务。连接断开要做资源释放，避免内存泄漏。

## 14、追问：Feign 调用 Python 服务要注意什么？

**口述：** 第一调大超时时间，Agent 推理耗时很长；第二处理序列化；第三做好异常捕获，处理服务不可用、调用失败；第四不要用 Feign 调用 SSE 流式接口，Feign 不适合流，流式要使用 WebClient。

# 简历上可以顺带写的技术亮点总结

- 采用 SpringBoot+LangGraph 双服务架构，实现多角色 Agent 协同 RAG 系统，分离业务与 AI 能力。
- 使用 LangGraph 构建状态图，实现路由、检索、工具调用、反思校验、回答组装五大 Agent，支持条件循环重试。
- RAG 层面实现 BM25 + 向量混合检索，引入交叉编码器重排，通过反思 Agent 缓解大模型幻觉。
- 基于 SSE 实现流式对话；针对 Agent 长耗时任务，基于 Redis 实现简易异步任务队列，解决接口超时问题。
- 严格做服务边界隔离，Python Agent 不直连业务库，通过回调 Java 接口获取业务数据，统一鉴权；使用 Redis 共享会话与 Agent 状态。
- Docker Compose 完成多服务编排，实现链路埋点日志、异常降级、循环次数防护等工程化处理。
