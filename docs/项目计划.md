# 多 Agent 协同 RAG 系统项目设计

你的背景：大四，技术栈 SpringBoot Java 后端 + Python LangGraph Agent 双服务，Milvus 向量库、Redis、Docker Compose。 目标：**避开玩具 Demo，做出工程化亮点，面试能深挖，区分网上烂大街的单 RAG 项目**。

> 核心定位：**多 Agent 协同知识库问答系统** 架构：Java (SpringBoot) 业务服务 + Python (FastAPI+LangGraph) Agent 服务，两个微服务。 不要做成 “输入问题出答案”，要加上**业务层、Agent 调度层、RAG 工程层、可观测性**。

## 整体架构分层（写简历、画图直接用）

1. **接入层（Java SpringBoot）** 前端请求入口、用户登录鉴权、会话管理、权限控制、参数校验、SSE 流式转发、任务管理、业务数据库 MySQL。

> 职责：**所有业务、权限、用户相关全部在这里，Python Agent 不碰 MySQL，不做鉴权**。

1. **Agent 服务层（Python FastAPI + LangGraph）【AI 核心】** 接收 Java 的请求，执行多 Agent 图调度：路由 Agent、检索 Agent、工具 Agent、反思校验 Agent、回答生成 Agent； 维护 Agent 状态、记忆；对接大模型 (Ollama/DeepSeek)；RAG 检索；向量库 Milvus。
2. **共享中间件**

- Redis：共享 session 会话、Agent 状态缓存、限流、任务状态存储
- Milvus：向量库
- MySQL：Java 独占，存储用户、知识库、对话记录
- Docker Compose：一键编排全部服务

## ✨真正拿分的亮点设计（重点，简历写 + 面试口述）

> 网上大部分项目：单 RAG，直接向量检索→大模型。 你的亮点要落在：**多 Agent 分工、RAG 优化、工程可靠性、服务拆分设计、问题规避**。

### 亮点 1：基于 LangGraph 的 5 个角色 Agent 协同（核心亮点）

不要写一个大 Agent 包揽全部，拆分工，体现 Agent 调度思维。

1. **路由 Agent**：判断用户 query 类型：知识库问答 / 需要调用工具 / 闲聊；做任务分发。
2. **检索 Agent**：负责 RAG，混合检索 BM25 + 向量检索，再经过重排器过滤无关文档。
3. **工具调用 Agent**：执行外部工具（例如查询业务数据，回调 Java 后端接口拿业务数据）。
4. **反思校验 Agent（自我校验）**：拿到检索结果后，做幻觉检测：判断文档是否足够回答问题；如果证据不足，触发重新检索。
5. **回答组装 Agent**：整理上下文，输出最终回答，输出引用来源。

> LangGraph 实现循环：证据不足 → 回到检索 Agent 二次检索，形成闭环。 面试话术： “我没有用单轮调用，而是用 LangGraph 构建状态图，实现多 Agent 流转，支持循环重试；Agent 之间通过共享 State 传递上下文，支持断点保存状态到 Redis。”

### 亮点 2：RAG 工程优化（拒绝简单向量查询）

这一块是面试官最爱追问 RAG 项目的地方：

1. **混合检索 BM25 + 向量检索**，结果融合，弥补纯向量丢失关键词的问题。
2. **交叉编码器重排（Cross‑Encoder）**，对初筛文档做二次打分，过滤噪声。
3. **幻觉检测：反思 Agent 校验检索片段和答案的一致性**，没有相关证据就拒绝回答，减少幻觉。
4. 知识库文档预处理：分块策略优化，语义分块，重叠窗口；支持文档上传、增量更新向量库。

> 注意：**文档上传、知识库管理接口放在 Java 后端**，Java 接收文件，做解析，再调用 Python 服务接口执行向量化入库。Python 不直接接收用户上传文件。

### 亮点 3：双服务边界设计（非常体现工程思维）

> 面试官必问：为什么 Java 和 Python 分开？职责怎么划分？

1. Java：用户、权限、知识库元数据、对话记录存储、鉴权、对外接口。
2. Python Agent：只做 AI 逻辑，**禁止直连 MySQL 业务库**。Agent 需要业务数据，通过 HTTP 回调 Java 接口获取，带上鉴权参数。
3. 会话打通：Java 生成 sessionId，传给 Agent；对话记忆、Agent 运行状态存在共享 Redis，两边都可读。
4. 两种交互模式：
   - 实时对话：SSE 流式输出，Java 做 SSE 透传，前端打字机效果。
   - 长耗时任务（大文档解析、复杂多轮 Agent 推理）：接入 Redis List 做简易消息队列，Java 提交任务，Python 消费，前端轮询任务状态，规避 HTTP 超时。

> 踩坑点要准备口述：Agent 推理耗时久，同步接口容易超时，因此设计两种交互模式。

### 亮点 4：异常与降级策略（很多学生项目缺失）

1. Agent 服务不可用时，Java 做服务降级，返回友好提示。
2. 大模型调用失败、向量库查询异常捕获。
3. 限制最大 Agent 循环次数，防止 LangGraph 无限死循环。
4. 会话记忆做窗口裁剪，防止上下文无限膨胀。

### 亮点 5：可观测性（加分项，拉开差距）

1. Agent 每一步状态落日志：路由到哪个 Agent、检索召回多少文档、重排后保留多少、是否触发二次检索。
2. 记录 token 消耗、检索耗时，方便后续调优。

> 不用上 ELK，打印结构化日志即可，简历写上：对 Agent 执行链路做埋点日志，便于排查幻觉、检索失败问题。

### 亮点 6：容器化工程交付

整套项目使用 Docker Compose 编排：Java、Python‑Agent、Milvus、Redis 一键启动。

> 体现你不是只写业务代码，懂服务部署。

## ❌不要做的，避免变成玩具项目

1. ❌不要 Java Process.exec 调用 Python 脚本，绝对不要写进简历。
2. ❌不要把业务数据库交给 Python 访问，权限全部交给 Java。
3. ❌不要写一个万能 Agent，所有逻辑堆在一起，一定要拆分多角色 Agent。
4. ❌不要只有一个页面，只做问答；要有知识库管理、用户会话管理的业务接口。

## 面试高频问答（口述版，你可以直接背）

**Q：为什么不全部用 Java 写 Agent？**

> SpringAI、LangChain4j 可以实现简单工具调用，但缺少成熟的图状态引擎，多 Agent 循环、分支流转、状态持久化需要大量手写。项目需要实现反思后重新检索的闭环，LangGraph 生态更成熟，开发维护成本更低，因此把 Agent 拆成独立 Python 服务；业务鉴权、数据库能力交给 Java。

**Q：为什么不全用 Python 开发？**

> 项目包含完整用户、权限、知识库管理业务模块，Java 企业后端生态成熟，事务、权限控制更方便；拆分之后，Agent 服务可以独立扩容，AI 的压力不会影响核心业务服务。

**Q：Agent 需要业务数据怎么办？**

> Python Agent 不直接访问业务 MySQL，通过回调 Java 提供的业务接口获取业务数据，鉴权逻辑统一由 Java 处理，保证数据安全。

**Q：怎么解决 RAG 幻觉？**

> 一方面通过混合检索加重排提升召回质量；另一方面设计反思校验 Agent，对比检索片段与生成答案，证据不足时触发二次检索，没有足够来源则拒绝编造答案。
